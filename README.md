# 📍 myMap myPlan (가제) - 지도 기반 계획 세우기 프로젝트
> 사용자가 **장소를 검색하면**, 해당 장소의 **이미지, 영상, 위치, 길찾기, 택시 이동**까지 한 번에 확인할 수 있는 **로컬 콘텐츠 탐색 웹앱**입니다.  
> `Next.js`, `recoil`, `PWA`, `OAuth`, `Naver Maps API`, `T Maps API`, `YouTube` 등 다양한 기술을 통합한 **실전형 포트폴리오 프로젝트**입니다.


## 👏 최근 작업  
- log page vercel에 배포 이슈 (25.08.25)  
  : plan의 기록을 보여주는 log 페이지를 서버 컴포넌트로 보여주길 원함  
  [이슈]  
&nbsp&nbsp(1) 로컬서버에서 시각화 된 데이터가 vercel에서는 시각화 되지 않음  
  [원인]  
&nbsp&nbsp(1) 기존의 firebase Web SDK를 사용했는데 이것은 클라이언트 전용, 브라우저에서 쓰도록 되어 있으므로 -> 서버 컴포넌트에서는 사용하지 못함  
  [해결]  
&nbsp&nbsp(1) admin sdk(firebase-admin)를 사용해야 함, admin sdk는 인증/보안 규칙을 무시하고 서버 자격 증명으로 접근 가능  
&nbsp&nbsp&nbspadmin sdk가 클라이언트로 노출하면 문제가 생김! -> 서버에서만 사용되도록 해야 함, 그에 대한 안전 장치로 해당 파일 최상단에 import 'server only'를 작성  
&nbsp&nbsp(2) Next.js 플래그 지정, next js의 app Router는 기본적으로 '정적 최적화(빌드 시점에 페이지를 미리 렌더링하여 html로 저장, ssg/isr, ppr 포함)'와 'Edge Runtime(네트워크 왕복 시간을 최소화 하여 응답에 대한 시간을 줄이는 방법)'을 최대한 활용하려 한다  
&nbsp&nbsp&nbsp하지만 firebase Admin sdk처럼 node 전용 라이브러리는 edge runtime이 불가하고 항상 최신 DB 읽기가 필요하므로 정적 최적화가 합당하지 않다 그리하여  
&nbsp&nbsp&nbspruntime = nodejs(Edge가 아닌 node.js 런타임에서 실행되도록 강제), dynamic = force-dynamic(정적 빌드/캐싱을 막고 매 요청마다 서버 실행 하도록 강제, revalidate = 0(ISR/캐싱을 막고 매 요청마다 최신 데이터 가져오도록)의 설정을 주어야 한다  
  [ssr을 선택한 이유]  
&nbsp&nbsp(1) 백엔드 서버를 별도로 두지 않고 firestore로 데이터를 직접 가져오기 위해 선택함  
&nbsp&nbsp(2) 추후 계정 마다 많은 기록들을 load하려면 브라우저가 렌더링 하기 보다, 서버에서 렌더링 하는 게 더 멀리 본다고 생각함  
&nbsp&nbsp(3) 단순 리로드로 데이터를 읽고 삭제하는 기능만 필요하기 때문.

  네이버 정책상 경로 관련 api는 ip주소로 호환하기 때문에, proxy 서버를 cdn(render)에 배포하여 데이터를 받음 -->  
  [이슈]  
       (1) 네이버 api로 이동 경로를 받아오기가 어려움  
       (2) 네이버 api로는 도보 이동 경로를 받아올 수가 없음  
       (3) proxy 서버로 사용한 render는 15분 동안 요청이 없으면 자동으로 Sleep 상태로 전환, 다시 요청하면 재기동 후 응답하는데 시간이 몇 초 지연 발생함
  
  [해결]  
       T map api로 도보 이동 거리 및 자동차 이동 거리를 데이터로 받아옴  
- 지도 api 연결을 server acition에서 api Route로 변경 --> 이유) api로 받아오는 데이터를 연산함으로  
- 7월 11일 작업 : 선택한 장소 리스트 삭제 기능 완료. 예를 들어,  
  광화문 == (자동차, 3km, 10분) ==> 경복궁 == (자동차, 19km, 25분) ==> 동대문 == (걷기, 5km, 13분) ==> 동대문역사문화공원  
  일 경우, 경복궁을 삭제하면, 다음과 같다  
  광화문 ====> 경복궁 ====> 동대문 == (걷기, 5km, 13분) ==> 동대문역사문화공원  
  으로 적용  
- 7월 13일 작업 : 계획 구간(위치) 삭제 후 새로운 경로 지정. 예를 들어,  
  광화문 == (자동차, 3km, 10분) ==> 경복궁 == (자동차, 19km, 25분) ==> 동대문 == (걷기, 5km, 13분) ==> 동대문역사문화공원  
  일 경우, 경복궁을 삭제하면, 다음과 같다  
  광화문 == (자동차 및 걷기 --> 저장 및 이전 --> 새로운 경로로 표시) ==> 동대문 == (걷기, 5km, 13분) ==> 동대문역사문화공원  
- 7월 15일 고민 : 로그인(소셜 로그인)관련해서 다시 점검해보았다.기존에는 next-auth + fireStore를 사용하려 하였으나, firesbase-auth + fireStore 조합을 사용하기로 결정  
  이유는 다음과 같다. 프론트 만으로 빠르게 만들 수 있다는 것. 서버가 불필요하고 가입하는 유저 정보도 자동으로 저장할 수 있다.  
  firebase-auth는 csr을 기본으로하나 firebase admin sdk를 사용하면 ssr로도 가능하다 그로인해 보안에도 좋은 영향을 줄 수 있다  
- 7월 17일 작업 : 소셜 로그인 기능 작업, firebase-auth로 인증 후, firestore에 유저 정보 저장 기능하도록 구현함. firease-auth는 token(accessToken과 refreshToken)을 자동으로 관리해줌 따라서,
  토근 관련한 코드를 별도로 작성할 이유가 없음.
  유저 정보 저장은 localStorage에 저장함.

## 🚀 프로젝트 목표
